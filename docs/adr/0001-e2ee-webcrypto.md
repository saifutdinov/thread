# ADR 0001: сквозное шифрование на WebCrypto с привязкой к устройству

Статус: принято (2026-10-16)

## Контекст

Чат для близких людей, который каждый может запустить на своём сервере. Требования: сообщения доступны только участникам чата, вход привязан к устройству, работа из любого мобильного браузера без установки приложения. Сервер - один Docker-контейнер с SQLite.

От чего защищаемся: хостер или изъятие диска, утечка БД и бэкапов, перехват трафика, украденный пароль, админ сервера в пассивном режиме.

## Решение

Свой протокол из стандартных примитивов WebCrypto (без сторонних крипто-библиотек):

| Что | Как |
|---|---|
| Ключи устройства | ECDH P-256 (обёртка ключей) + ECDSA P-256 (подписи), `extractable: false`, хранятся как `CryptoKey` в IndexedDB. Закрытая часть не покидает браузер. |
| Ключ чата | Случайный AES-256-GCM на каждую «эпоху» чата. |
| Доставка ключа чата | ECIES: эфемерный ECDH → HKDF-SHA256 (`connect/wrap/v1`, salt = эфемерный ключ) → AES-GCM, AAD `k:<epoch>`. 125 байт на устройство. Сервер хранит только обёрнутые копии (`chat_keys`). |
| Сообщение | `iv ‖ AES-GCM(JSON{t, a, rp})`, AAD `m:<chat>:<epoch>`; подпись ECDSA устройства отправителя над `AAD ‖ body`. |
| Реакция | AES-GCM эмодзи, AAD `r:<chat>:<msg>:<epoch>`. |
| Название группы | AES-GCM, AAD `t:<epoch>`. |
| Фото | Пережатие в браузере (EXIF/GPS удаляются), свой случайный ключ на файл, ключ лежит внутри зашифрованного сообщения. Сервер хранит непрозрачный blob. |
| Приглашение | Секрет 32 байта во фрагменте URL `#/i/<secret>` (не уходит на сервер и в логи). HKDF → `auth` (сервер хранит SHA-256(auth) как id) и `wrap` (шифрует набор ключей чата, известен только браузеру). |
| Новое устройство | Вход по паролю даёт статус `pending` без ключей и без доступа даже к метаданным. Своё одобренное устройство перешифровывает ключи всех чатов под новое. Оба экрана показывают код (4 эмодзи + 6 цифр из SHA-256 публичных ключей). Сразу активным устройство становится только у пользователя без чатов и без единого рабочего устройства. Известное устройство входит, подписав nonce; подпись проверяется до пароля. |
| Потеря всех устройств | Новое устройство просит помощи (`recovery`); участник общего чата сверяет код и перешифровывает ключи этого чата. Сервер принимает такой ответ только с ключами чатов, общих для обоих. |
| Ротация | Когда участник вступает или выходит, или когда отключают устройство, у чата ставится флаг `rotate`. Следующий отправитель создаёт новую эпоху и оборачивает ключ для всех активных устройств участников; сервер проверяет, что набор устройств полный и точный. Если одобрение пришло без ключа текущей эпохи (гонка с ротацией), флаг ставится снова. |
| Повторное приглашение в личный чат | Сначала ротация, в ссылку кладётся только текущий ключ: новый человек не прочитает прежнюю переписку. В группах новые участники видят историю, как в Telegram. |
| Push | Payload содержит шифротекст; service worker расшифровывает текст ключом из той же IndexedDB. С блокировкой и скрытием текста показывает только «Новое сообщение». |
| Вложения | Голосовые, кружочки и файлы шифруются как фото; тип, длительность, волна и имя файла лежат внутри зашифрованного сообщения. Пересылка: сервер делает копию шифротекста (hard link) в целевом чате, ключ файла едет в новом сообщении. |
| Коды безопасности | Один код на пару: SHA-256 от отпечатков наборов устройств обоих (отпечаток = SHA-256 отсортированных ключей устройств). После отметки «Коды совпадают» смена устройств собеседника показывает предупреждение: так видно и подмену устройств сервером. |
| Возраст ключа | Ключ чата старше 7 дней обязан смениться перед следующим сообщением: утёкший ключ раскрывает не больше недели переписки. |
| Звонки | WebRTC 1:1 в личных чатах. SDP и ICE-кандидаты шифруются ключом чата, AAD `call:<chat>:<id>:<kind>:<epoch>` (kind: offer, answer, ice, а при восстановлении связи reoffer и reanswer): сервер не может подменить DTLS-отпечатки и встать посередине или выдать один сигнал за другой. Звук и видео идут DTLS-SRTP напрямую или через свой TURN (coturn), который видит только шифротекст. Пароли TURN временные (HMAC, 12 часов). |
| Аватар | Картинка 256 px шифруется ключом чата отдельно для каждого чата пользователя, AAD `a:<chat>:<user>:<epoch>` (id владельца в AAD: сервер не выдаст чужой аватар за его). Сервер хранит шифротекст и номер версии; клиент сам докладывает аватар в чаты, где его нет или он зашифрован ключом старше текущего (личный чат после переприглашения). |
| Фото группы | Как аватар, AAD `p:<chat>:<epoch>`. |
| Предпросмотр ссылок | Выключен по умолчанию. Если включить, браузер отправителя просит сервер открыть страницу (сервер узнаёт ссылку, но не текст сообщения), собирает карточку с уменьшенной картинкой и кладёт её внутрь зашифрованного сообщения. Получатели ничего не загружают. Сервер ходит только на публичные адреса и порты 80/443, проверка в dialer на каждое соединение (защита от SSRF и DNS rebinding). |
| Бэкап сервера | Снимок базы раз в сутки шифруется [age](https://age-encryption.org) на открытый ключ владельца; закрытого ключа на сервере нет. Файлы и так зашифрованы на устройствах и уходят в S3 как есть. Файлы удалённых сообщений из бакета не удаляются: их ключи были только внутри удалённых сообщений и уходят из бэкапов вместе со старыми снимками. |

Метки протокола (`connect/wrap/v1`, `connect/invite/auth`, `connect/invite/wrap`, `connect-login:`) сохранили прежнее рабочее название проекта и заморожены вместе со строками AAD: это идентификаторы протокола, а не название продукта.

Пароль (`WordWord_1234`, ~37 бит, словарь из ~3500 простых слов EFF) - одновременно логин. На сервере хранится Argon2id(нормализованный пароль, pepper из env). Пароль сам по себе не открывает ни одного сообщения: нужен одобренный ключ устройства.

## Последствия

Плюсы: ноль зависимостей, нативная скорость, закрытые ключи физически не извлекаются, история доступна на новых своих устройствах.

Минусы и честные ограничения:
- Нет forward secrecy внутри эпохи: утёкший ключ чата раскрывает переписку этой эпохи. Смягчение: ротация при выходе участника/устройства и раз в неделю (см. «Возраст ключа»).
- Код приложения отдаёт сервер. Захваченный сервер может отдать подменённый JS и перехватывать новые сообщения на устройствах. Смягчение: строгий CSP, нет сторонних скриптов. Это ограничение любого E2EE в браузере.
- Список устройств пользователя удостоверяет сервер (нет кросс-подписи). Подменить устройство в обход человека нельзя (ключи передаёт только клиент по явному действию), но при ротации ключ оборачивается для всех устройств из серверного списка.
- Сервер видит метаданные: кто в каком чате, время и размер сообщений, имена, кто кому звонил, когда и сколько длился звонок (по сигналингу и логам TURN). При прямом соединении собеседники видят IP-адреса друг друга, как в любом WebRTC.
- Аватары и фото группы не подписываются устройством (как и название группы): участник чата в сговоре с сервером может подложить чужую картинку. Шифруются ключом текущей эпохи без принудительной ротации, поэтому человек, вышедший из группы, в сговоре с сервером может увидеть новое фото до ближайшей смены ключа.
- С включённым предпросмотром ссылок сервер видит адреса ссылок, которые отправляет этот человек.
- Блокировка приложения (PIN, Face ID через WebAuthn) только закрывает интерфейс: ключи устройства неизвлекаемые и не перешифровываются под PIN, так что от человека с доступом к профилю браузера она не защищает.
- Восстановление через собеседника опирается на человека: если собеседника обманут (не сверит код по телефону), злоумышленник с паролем получит полноценное устройство, в том числе право отключать чужие устройства этого аккаунта.
- На iPhone приложение с экрана «Домой» и Safari хранят данные раздельно, поэтому регистрироваться нужно уже в установленном приложении (ссылка-приглашение вставляется на экране входа).

## Отвергнутые варианты

- **Шифрование только на сервере** - хостер/админ читают всё, не выполняет требование.
- **Matrix Olm/Megolm (vodozemac WASM) или MLS** - аудированные библиотеки и forward secrecy, но +1-2 МБ WASM, медленнее на слабых телефонах, в разы сложнее и тяжелее с историей на новых устройствах. Вернуться к вопросу, если чат перерастёт круг близких.
