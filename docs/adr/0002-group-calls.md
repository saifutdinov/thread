# ADR 0002: групповые звонки через свой SFU LiveKit со сквозным шифрованием кадров

Статус: принято (2026-11-02)

## Контекст

Нужны групповые звонки в группах до 10 человек, со звуком и видео, стабильные, с минимальной задержкой и в духе ADR 0001: сервер не должен слышать и видеть звонок. Люди часто звонят из мобильных сетей (iPhone с приложением на экране «Домой», Android Chrome). Сервер один: VPS, на котором стоит Нитка.

Звонки 1:1 идут напрямую между устройствами (ADR 0001, «Звонки»). Для группы так не выйдет: без сервера каждый отправляет 9 потоков и принимает 9, звук держится до 6-8 человек, видео на телефонах до 3-4.

## Решение

- **SFU LiveKit** (`livekit/livekit-server`, Apache-2.0, закреплён по digest) в контейнере `sfu` рядом с приложением. Каждый отправляет звук и картинку один раз, SFU раздаёт их остальным, ничего не перекодируя. Он умеет:
  - несколько слоёв видео: 180p и 360p, их выбирают под каждого зрителя;
  - не отправлять слой, который никто не смотрит;
  - определять, кто говорит;
  - восстанавливать связь при смене сети.

  Клиент - `livekit-client`; он грузится только при входе в групповой звонок.
- **Сквозное шифрование кадров.** Каждый кадр шифруется в браузере до отправки (AES-GCM, E2EE-воркер LiveKit на Encoded Transform) ключом звонка. SFU пересылает шифротекст; в его логах треки помечены `encryption: GCM`.
  - **Ключ звонка** - 32 случайных байта, свои на каждый звонок. Начавший звонок запечатывает его ключом чата так же, как сигналинг 1:1, с AAD `call:<chat>:<id>:gkey:<epoch>` (новый `kind`, префикс `call:` прежний). Если чат ждёт смены ключа (новичок по ссылке, новое устройство), начавший сначала меняет его, как перед сообщением: иначе у новичка нет ключа, которым запечатан звонок.
  - **Сервер** хранит только этот шифротекст, пока звонок идёт, и отдаёт его участникам чата при входе.
  - **Браузер без Encoded Transform** (`isE2EESupported()` ложно) в звонок не входит. Без шифрования не соединяемся.
- **Пропуски.** Go-сервер выдаёт пропуск LiveKit (JWT HS256, 10 минут, дальше LiveKit продлевает его сам) только активному устройству участника группы. В пропуске:
  - комната - `c<chat>-<id>`, её задаёт сервер: id звонка, унесённый из одного чата, не открывает комнату другого;
  - участник - `<user>.<device>.<случайная часть>` без имени; имена клиент берёт из чата сам. Случайная часть нужна, чтобы две вкладки одного устройства не выбивали друг друга.

  Больше 10 устройств в звонок не пускают: сервер отвечает `call_full`, LiveKit держит `max_participants: 10`.
- **Сигналинг.** Сигналинг LiveKit (WebSocket, порт 7880) идёт через приложение по `/lk`, только для вошедших устройств и без нашей cookie сессии, так что Caddy настраивать не нужно. Наружу открыт не он, а только медиа:
  - **`7882/udp`:** один порт на все звонки. Диапазон портов легче заблокировать, и его надо открывать целиком;
  - **`7881/tcp`:** ICE-TCP там, где UDP не проходит.
- **Кто в звонке** сервер хранит в памяти:
  - устройство входит запросом `POST /api/chats/{id}/call`, только если у него открыт сокет (иначе `offline`: его никто бы не вывел);
  - выходит запросом `DELETE` или когда закрывается его последний сокет;
  - с новым сокетом входит снова. Звонок, который сервер забыл при перезапуске, приложения в нём возвращают сами (`rejoin` с тем же запечатанным ключом), не звоня всем заново.

  Начало звонка звонит остальным участникам: событие по сокету и push. По тому же лимиту, что и вызов 1:1, участник не может звонить всем без остановки. Изменения состава уходят событием `gcall state`, а приложение при открытии запрашивает идущие звонки (`GET /api/calls/group`) для плашки «Присоединиться».
- **Звук.** Opus около 32 кбит/с моно, включены DTX (молчащие почти не тратят трафик) и FEC в потоке. RED выключен: он удваивает звук для каждого слушателя и не проходит через шифрование кадров. Шумоподавление и эхоподавление встроенные в браузер, как в звонках 1:1.

## Последствия

- Сервер и SFU видят метаданные звонка:
  - кто и когда в нём;
  - у кого включены микрофон и камера;
  - кто говорит (уровень звука идёт открыто в RTP-заголовке);
  - размеры пакетов.

  Звук и картинку не видят. SDP групповых звонков сервер видит (в 1:1 он запечатан). Подменить его бессмысленно: DTLS всё равно заканчивается на SFU, а содержимое защищает шифрование кадров.
- Ключ один на звонок. Человек, которого убрали из группы посреди звонка, знает этот ключ, но нового пропуска не получит, а комнату другого чата его id звонка не откроет. Уже открытое соединение с LiveKit сервер пока не разрывает: ни у убранного из группы, ни у отключённого устройства (до конца этого звонка).
- Кто вошёл в группу уже после начала звонка, в этот звонок не попадёт: ключ запечатан до него. Попадёт в следующий.
- После перезапуска приложения звук и видео идут дальше (LiveKit их не прерывает); список звонков возвращается, как только приложения в звонке переподключат сокет.
- TURN для групповых звонков не используется: coturn отказывается пересылать на собственный IP сервера. Резерв для сетей без UDP и TCP 7881 - TURN по TLS на 443 (отдельное имя и сертификат, разбор SNI перед Caddy). Это следующий шаг.
- Там, где мобильный интернет работает по белым спискам, сервер недоступен целиком, не только звонки. Кодом это не решается.

## Отвергнутые варианты

- **Без сервера (каждый с каждым)** - не держит 10 человек с видео, телефоны греются.
- **Свой SFU на Pion в нашем Go-сервере** - месяцы работы над переключением слоёв, ключевыми кадрами и оценкой полосы, LiveKit это уже умеет.
- **mediasoup, Janus, Jitsi** - больше склейки (Node, C или Java со своими сервисами), Janus под GPL, шифрования кадров из коробки нет или оно привязано к своему стеку.
- **Krisp** для шумоподавления в LiveKit - только в их облаке.
